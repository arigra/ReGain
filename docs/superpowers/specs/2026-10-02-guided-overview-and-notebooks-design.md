# Guided overview and guided notebooks

Date: 2026-10-02 · Status: draft for review · Extension version target: 1.2.0

## Why

ReGain 1.1.16 builds the map and the notebooks alone and hands them over. The user wants to be part of shaping the overview, so the subjects match how they think about the project, and wants each notebook to guide them through a subject from start to finish, at a depth they control. Insights 13 (three depth levels), 17 (the system sets the pace), 24 (cost in proportion) and 25 (the map is built with the user) apply.

## What the user said (decisions)

- The conversation lives **inside the ReGain page**, under the map.
- **Map first, then talk.** The map builds as now, with live progress; the conversation starts when it is ready.
- **No question about the user's familiarity** with the project. The agent explains first.
- The agent **explains the project in simple terms**, then **offers the subjects** it wants to introduce. The number fits the project: 4-6 for radSeq, many more for a large multi-algorithm project.
- User and agent **settle the subjects together**. The agent decides per message whether it needs to read code.
- Map changes: **the user asks, it is applied**. Changes the agent only suggests wait for Apply / Skip.
- A **visible, correctable record** of what the user knows, cares about, and what is open.
- After the overview is right, notebooks work **as today** (pick a subject or part, create a notebook), but the notebook **guides the user from start to finish**.
- Notebooks open at **Short**; each step can **go deeper** on demand (Walkthrough, then Full).
- **All names and explanations are simple and intuitive.** This is hard already; simplify the right amount.
- Conversation memory: **a fresh agent call per message**, with the history in the prompt (no resumed sessions).

## Not in scope

- A chat for exploring sub-parts. After the overview, the "+" button and notebooks work as today.
- The `/regain` skill in Claude Code. It is not changed by this work.
- Resumed agent sessions, file-notes caches, time limits.

## Part 1 · The overview conversation

### What the user sees

Below the map, a chat area; beside it, a small box "What ReGain thinks you know" with three short lists: knows, cares about, open.

1. The map finishes building.
2. The agent's first message, generated from the map: 2-4 simple sentences on what the project is for and how far it got, then the subjects it wants to introduce, one plain line each, ending with an invitation to say what to merge, split, add or drop.
3. The user replies in free text. While the agent works, the reply bubble shows live steps (the same events as the progress panel) and elapsed time.
4. Requested map changes are applied at once; the reply says what moved and changed subjects glow briefly on the map. Changes the agent suggests on its own show Apply / Skip.
5. If a subject is selected on the map, the message carries it, so "what is this?" works without naming it.

Replies are short (2-4 sentences), one topic at a time, never a quiz.

### One message, end to end

- Webview posts `{type: "chat", text, selectedId}`.
- The extension builds the prompt from: project summary, current top-level subjects (name, kind, purpose, key files), selected subject, the last 10 messages, the record, the project budget, the plain-language rule, and a step allowance (`chat` budget: small 10 / medium 15 / large 20 steps; hard cap 2.5x on Claude Code).
- One agent call (Claude Code or Codex) with a `chat` schema:
  - `reply`: string
  - `apply`: map operations the user asked for
  - `suggest`: map operations the agent proposes (shown as Apply / Skip)
  - `record`: `{knows: [], cares: [], open: []}`, the full updated lists (short phrases)
- Map operations, each with a short plain reason: `rename {id, name}`, `describe {id, purpose}`, `merge {ids, name, purpose}`, `split {id, into: [{name, purpose, kind, sources}]}`, `add {name, purpose, kind, sources, after}`, `remove {id}` (moves its files to "Earlier work" or drops the subject when it has none), `move {id, after}`.
- The extension validates before applying: ids exist; every `sources` path exists inside the project; names are 2-5 words; a subject keeps at least one source. Invalid operations are dropped and the reply gets one line saying what could not be applied and why.
- Applied operations go through `saveMap`, so `semantic-map.json` and `overview.html` update together; ids of changed subjects are posted to the page for the glow.
- `suggest` operations are stored with the message; Apply runs the same validation, Skip records the refusal.

### Opening message

Generated by a separate small call right after the map is saved (same schema, empty history, `apply` must be empty). If a conversation already exists, it is shown instead and no call is made.

### Storage (in `.regain/`)

- `conversation.json`: `[{role, text, at, applied, suggested, status}]`. The page renders it on load, so redraws and restarts keep the chat.
- `learner.json`: `{knows, cares, open, updatedAt}`. Shown in the box; read by notebook calls.
- `agent-runs.jsonl`: one line per chat call too (`kind: "chat"`).

### Map prompt changes

- Plain-language rule added to every prompt that names or explains: everyday words, short names (2-4 words), say what a thing does before how, no jargon a returning developer would have to decode; do not oversimplify into vagueness.
- The budget's subject range stays the starting point; the conversation adjusts the final count.

## Part 2 · Guided notebooks

### Shape

Every notebook is one path through the chosen subject or part:

- **Start**: what question this part answers and what goes in.
- **Steps** in the order things happen. Each step: a real output or concrete fact first, then 2-3 plain sentences on what happens and what to notice.
- **End**: what comes out and where it goes next (link to the next subject's notebook if it exists).

### Three depths, per step

- **Short** (what the notebook opens with): one screen, the story only, 3-5 steps, no code. Generated by the "Create notebook" call.
- **Walkthrough**: for one step, the few lines that do the work (excerpts within the budget's line limit) and what to notice in them.
- **Full**: for one step, every piece from entry to output, the details that bite (red lines, written to `importance-reviews.json` as today), and one runnable check where a safe one exists.

Each step ends with a "Go deeper" button while a deeper level remains. Pressing it runs one agent call for that step only, with live progress shown in place, and replaces that step's section with the deeper version. Other steps are untouched.

### Format

Each step is a `##` section followed by a marker line:

```
## Fit the simulator to real recordings
<!-- regain:step id=fit depth=short -->
```

- The notebook view renders a "Go deeper" button after a step whose depth is `short` or `walkthrough`, and hides the marker.
- The view posts `{type: "deepenStep", id}`; the provider forwards it to the extension, which reads the section, runs a `step` agent call (schema: `{explanation, sources: [{path, role, startLine, endLine}], demonstrations, decisions, depth}`), rewrites only that section in the `.regain.md`, and the view refreshes.
- The step prompt gets: the subject, the whole Short page (for context), the step's current text, the target depth, the record from `learner.json`, the budget, and the plain-language rule.

### Notebook prompt changes

- "Create notebook" asks for the Short path only: overview, ordered steps (3-5) with a one-line "what to notice" each, end. Sources per step are the files that the deeper levels will start from, not shown at Short.
- The record from `learner.json` is included: skip what the user already knows, lean toward what they care about.
- Kind still shapes the path: code (follows data), experiment (question, setup, result, caveats), status (milestones). Experiment and status steps go at most to Walkthrough.

## Progress

All new calls (`chat`, opening message, `step`) use the existing live progress: the output panel and notification, plus the chat bubble or the step being deepened shows the latest step and elapsed time.

## Errors

- Agent failure or cancellation: the chat bubble or step shows "Stopped: reason" with a Retry button; nothing on disk changes.
- Invalid map operations: dropped, reported in one line in the reply.
- A step marker missing or changed on disk since rendering: the deepen is refused with a message asking to reopen the notebook.
- Running out of the step allowance: the existing "used its whole allowance" error, shown in place.

## Testing

- Unit: map operation validation and application (each op, invalid ids, missing files, name length); conversation and record storage; prompt contents (history trimmed to 10, selected subject, record, plain-language rule); step marker parsing and section replacement.
- Page: the chat renders history from `conversation.json`, Apply / Skip post the right messages, changed subjects get the glow class.
- Notebook view: "Go deeper" appears for `short` and `walkthrough`, not for `full`; the marker is hidden.
- End to end, by hand on radSeq: the map builds, the opening message lists 4-6 plain subjects, a merge request updates the map, Short notebook opens, one step deepens twice.

## Build order

1. Plain-language rule in the existing prompts.
2. Chat schema, map operations, storage, and the chat area on the page.
3. Opening message.
4. Short notebooks with step markers.
5. "Go deeper" in the notebook view and the step call.
