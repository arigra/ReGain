# Guided overview and guided notebooks

Date: 2026-10-02 · Status: built in 1.2.0, awaiting the user's comments

## Why

ReGain 1.1.16 builds the map and the notebooks alone and hands them over. The user wants to be part of shaping the overview, so the subjects match how they think about the project, and wants each notebook to guide them through a subject from start to finish, at a depth they control. Insights 13 (three depth levels), 17 (the system sets the pace), 24 (cost in proportion) and 25 (the map is built with the user) apply.

## What the user said (decisions)

- The conversation lives **inside the ReGain page**, under the map.
- **Map first, then talk.** The map builds as now, with live progress; the conversation starts when it is ready.
- **No question about the user's familiarity** with the project. The agent explains first.
- The agent **explains the project in simple terms**, then **offers the subjects** it wants to introduce. The number fits the project: 4-6 for radSeq, many more for a large multi-algorithm project.
- User and agent **settle the subjects together**. The agent decides per message whether it needs to read code.
- Map changes: **the user asks, it is applied**. Changes the agent only suggests wait for Apply / Skip.
- A **visible, correctable record** of what the user knows, cares about, and what is open.
- After the overview is right, notebooks work **as today** (pick a subject or part, create a notebook), but the notebook **guides the user from start to finish**.
- ~~Notebooks open at **Short**; each step can **go deeper** on demand (Walkthrough, then Full).~~ Revised 2026-10-03: a notebook is written **whole in one go**, then reviewed. See "Whole notebooks, written then reviewed" below.
- **All names and explanations are simple and intuitive.** This is hard already; simplify the right amount.
- Conversation memory: **a fresh agent call per message**, with the history in the prompt (no resumed sessions).

## Not in scope

- A chat for exploring sub-parts. After the overview, the "+" button and notebooks work as today.
- The `/regain` skill in Claude Code. It is not changed by this work.
- Resumed agent sessions, file-notes caches, time limits.

## Part 1 · The overview conversation

### What the user sees

Below the map, a chat area; beside it, a small box "What ReGain thinks you know" with three short lists: knows, cares about, open.

1. The map finishes building.
2. The agent's first message, generated from the map: 2-4 simple sentences on what the project is for and how far it got, then the subjects it wants to introduce, one plain line each, ending with an invitation to say what to merge, split, add or drop.
3. The user replies in free text. While the agent works, the reply bubble shows live steps (the same events as the progress panel) and elapsed time.
4. Requested map changes are applied at once; the reply says what moved and changed subjects glow briefly on the map. Changes the agent suggests on its own show Apply / Skip.
5. If a subject is selected on the map, the message carries it, so "what is this?" works without naming it.

Replies are short (2-4 sentences), one topic at a time, never a quiz.

### One message, end to end

- Webview posts `{type: "chat", text, selectedId}`.
- The extension builds the prompt from: project summary, current top-level subjects (name, kind, purpose, key files), selected subject, the last 10 messages, the record, the project budget, the plain-language rule, and a step allowance (`chat` budget: small 10 / medium 15 / large 20 steps; hard cap 2.5x on Claude Code).
- One agent call (Claude Code or Codex) with a `chat` schema:
  - `reply`: string
  - `apply`: map operations the user asked for
  - `suggest`: map operations the agent proposes (shown as Apply / Skip)
  - `record`: `{knows: [], cares: [], open: []}`, the full updated lists (short phrases)
- Map operations, each with a short plain reason: `rename {id, name}`, `describe {id, purpose}`, `merge {ids, name, purpose}`, `split {id, into: [{name, purpose, kind, sources}]}`, `add {name, purpose, kind, sources, after}`, `remove {id}` (moves its files to "Earlier work" or drops the subject when it has none), `move {id, after}`.
- The extension validates before applying: ids exist; every `sources` path exists inside the project; names are 2-5 words; a subject keeps at least one source. Invalid operations are dropped and the reply gets one line saying what could not be applied and why.
- Applied operations go through `saveMap`, so `semantic-map.json` and `overview.html` update together; ids of changed subjects are posted to the page for the glow.
- `suggest` operations are stored with the message; Apply runs the same validation, Skip records the refusal.

### Opening message

Generated by a separate small call right after the map is saved (same schema, empty history, `apply` must be empty). If a conversation already exists, it is shown instead and no call is made.

### Storage (in `.regain/`)

- `conversation.json`: `[{role, text, at, applied, suggested, status}]`. The page renders it on load, so redraws and restarts keep the chat.
- `learner.json`: `{knows, cares, open, updatedAt}`. Shown in the box; read by notebook calls.
- `agent-runs.jsonl`: one line per chat call too (`kind: "chat"`).

### Map prompt changes

- Plain-language rule added to every prompt that names or explains: everyday words, short names (2-4 words), say what a thing does before how, no jargon a returning developer would have to decode; do not oversimplify into vagueness.
- The budget's subject range stays the starting point; the conversation adjusts the final count.

## Part 2 · Guided notebooks

### Shape

### Whole notebooks, written then reviewed (revised 2026-10-03)

The Short / Walkthrough / Full design was dropped after the first real page (radSeq, "Test useful generation"). Its problems: the code cut every field at 1200 characters, so deepened steps stopped mid-sentence. The agent put excerpts in its prose and the code added them again under file-name headings, so excerpts appeared twice. The overview prompt asked for "what question and what goes in", so the verdict (a copying check that weakens the main gain) was buried in step 2. Each step was deepened alone, so no call owned the story. The user also does not want to ask for each step.

Now "Guide me through this" writes the whole notebook:

1. **Write** (`detail` call). The agent fills a strict structure: `title`, `verdict`, `terms`, `sections` (each `heading`, `takeaway`, `body`, `excerpts` of `{path, startLine, endLine, heading, notice}`, `demonstrations`), `unresolved`, `evidence`, `decisions`. Prose fields never carry code or headings. The prompt gives the rubric, the limits and a model notebook from another project (`examples/notebook-example.json`), and asks the agent to decide the verdict before planning sections.
2. **Check** (code, `guide.js`). Hard errors: length limits, empty fields, file-name or repeated headings, missing files, bad or overlong line ranges, the same lines shown twice, code blocks or headings in prose, repeated open questions. Warnings: numbers in the prose that appear in no cited file, a body that repeats its takeaway.
3. **Review** (`review` call). A second agent scores the draft on the rubric (1-5 per criterion), checks claims against the files, lists each problem with its fix, and returns the improved notebook. Its version wins unless it breaks more hard rules than the draft.
4. **Fix** (`fix` call, only while hard errors remain). Fixes exactly the listed errors.
5. **Render and save** (code). The page is laid out from the fields: verdict under the title, "Words used here", one `##` per section with its takeaway and body, one `###` per excerpt named by its idea, and "Open questions" once at the end. Prose is never cut. Excerpts that still break a rule are dropped or cut, and each repair is recorded. Next to the page, `capability-<id>.guide.json` keeps the draft, both checks, the review's scores and fixes, and the repairs.

The rubric: verdict first, one story, headings name ideas, nothing twice, numbers mean something, terms explained, excerpts earn their place, readable, accurate, open questions are real.

`scripts/guide-eval.js <project> <subject-id> [--judge]` runs the same pipeline outside VS Code and prints the checks, scores, fixes, repairs, and each call's time and cost. With `--judge`, a fresh review scores the final page. radSeq's subjects are the test cases.

Kind still shapes the sections: code (follows data), experiment (question, setup, result, caveats), status (milestones).

## Look and feel (shipped in 1.1.17; the new parts follow it)

- Explanations are content: full text colour, readable size and line length. Only genuinely skippable details are dimmed (line numbers, kernel state, "Source:" lines, file counts, the not-yet-checked list).
- Subject kinds have their own colour and label: code (teal), experiment (amber), status (violet).
- A subject's flow is a numbered path joined by a line.
- Notebook steps carry "Step n of N" and a line down the side of the path; expected results stand out as a callout.
- Every prompt carries the plain-and-accurate rule: simple everyday words, names of 2-4 words that say what the thing does, concrete facts checked against the source, no filler.

## Progress

All new calls (`chat`, opening message, and the notebook's `detail`, `review` and `fix`) use the existing live progress: the output panel and notification, plus the chat bubble shows the latest step and elapsed time.

## Errors

- Agent failure or cancellation: the chat bubble shows "Stopped: reason" with a Retry button. Nothing on disk changes. A failed review or fix keeps the best version so far and says so.
- Invalid map operations: dropped, reported in one line in the reply.
- Running out of the step allowance: the existing "used its whole allowance" error, shown in place.

## Testing

- Unit: map operation validation and application (each op, invalid ids, missing files, name length); conversation and record storage; prompt contents (history trimmed to 10, selected subject, record, plain-language rule); notebook checks, rendering, and the write, review and fix flow with fake calls.
- Page: the chat renders history from `conversation.json`, Apply / Skip post the right messages, changed subjects get the glow class.
- Notebook view: steps are numbered, open questions are not a step, older step markers stay hidden.
- End to end, by hand on radSeq: the map builds, the opening message lists 4-6 plain subjects, a merge request updates the map, and `scripts/guide-eval.js` writes a notebook with no hard errors left.

## Build order

1. Plain-language rule in the existing prompts.
2. Chat schema, map operations, storage, and the chat area on the page.
3. Opening message.
4. Whole notebooks: write, check, review, fix, render (replaced Short notebooks and "Go deeper" on 2026-10-03).

## Added while building

- **Project index and reading record.** Before the map is built, every file is indexed without AI (definitions, project imports, entry points) and given to the agent. The files the agent opens are tracked from its live steps, and the overview shows how many code files it read and which it did not.
- **Isolated agent calls.** Claude Code calls run without the user's plugins, hooks, skills and extra tool servers. On radSeq this cut the opening message from 6 minutes and $0.98 to 2.5 minutes and $0.46. A follow-up message takes about 20 seconds.
- **Merges keep the first subject's id**, and suggestions about subjects that no longer exist are marked outdated.

## Built in 1.3.0

- **Every file is read.** Code, configs, job scripts, notebooks, results, archive and docs, by parallel readers with the text in the prompt, cached by content. Docs are claims checked against the code. On radSeq (268 files): 72 s and $1.68 with Claude Code, 2.7 min with Codex, first time. Later rebuilds reread only changed files.
- **Story, state, roles, terms, open questions** are new map fields. The page shows the story in three lines, subjects as numbered boxes in reading order with arrows, a state on every subject and step, terms with hover text, and open questions you can answer in the chat.
- **Your path:** "Start here", "I've got this", ticks on the boxes.
- **Actions with usual times**, the guide beside the map (a bottom drawer on narrow editors), and an opening message that tells the story instead of repeating the page.
- **Reader cost findings:** hidden thinking cost 8,000+ tokens per call for notes of about 100 words. Turning it off made reading 4 times faster and cheaper with notes of the same quality.
